包装类与 Object： 基本类型的对象形态

泛型不能写 int，集合不能存 8 种基本类型，null 也无法用 int 表示——于是有了包装类。自动装箱让你写得爽，但缓存、空指针、== 比较这三个坑，几乎每个 Java 程序员都栽过。

约 60 分钟 6 个知识点 3 个面试高频点 前置：第 06 章

学完这一章，你应该能够

  • 说清包装类存在的三个理由
  • 解释装箱与拆箱底层调用了什么
  • 用缓存机制解释 127 与 128 的差异
  • 识别自动拆箱引发的空指针
  • 正确重写 equals 与 hashCode
  • 知道什么时候必须用 BigDecimal

7.1为什么需要包装类

Java 是「面向对象」的语言，但基本类型不是对象。

这个矛盾在三个地方暴露得很明显。第一，泛型和集合只接受对象：List<int> 编译不过，必须写 List<Integer>，因为泛型在编译后会类型擦除，底层统一按 Object 处理。第二，有些业务需要「没有值」：数据库里一个字段可能是空，int 无法表达「空」，只能用 Integer 的 null。第三，需要对象提供的方法：把字符串转成数字、求最大值、转二进制，这些方法都挂在包装类上。

基本类型包装类父类常用能力
byte / shortByte / ShortNumberparseByte、valueOf
intIntegerNumberparseInt、toBinaryString、MAX_VALUE
long / float / doubleLong / Float / DoubleNumberparseXxx、isNaN、isInfinite
charCharacterObjectisDigit、isLetter、toUpperCase
booleanBooleanObjectparseBoolean、valueOf

普通数值类型的包装类都继承自抽象类 Number，因此它们共享 intValue()、doubleValue() 这类拆箱方法。Character 和 Boolean 不参与数值体系，直接继承 Object。

7.2装箱、拆箱与缓存

自动转换是语法糖，背后是 valueOf 与 xxxValue 两个方法。

装箱是把基本类型包成对象，调用 Integer.valueOf(100)；拆箱是从对象取出基本值，调用 intValue()。Java 5 之后这两步可以自动完成，所以你写 Integer i = 100; 编译器会补上 valueOf。

关键在于 valueOf 不是简单地 new。为了减少对象创建，JDK 预先缓存了 -128 到 127 之间的所有 Integer 对象。传进去的值落在这个区间，直接返回缓存里的现成对象；超出范围才新建。这就是那个著名面试题的答案来源。

缓存区间的影响java
Integer a = 127, b = 127;
System.out.println(a == b);      // true，同一个缓存对象

Integer c = 128, d = 128;
System.out.println(c == d);      // false，各自 new
System.out.println(c.equals(d)); // true，比较内容

Integer e = new Integer(127);    // 强制新建，不查缓存

受同样机制影响的还有 Byte、Short、Long（范围也是 -128~127）、Character（0~127）和 Boolean（TRUE/FALSE 两个常量）。但记住一个结论就够了：包装类的比较永远用 equals，不要依赖缓存区间。

为什么缓存上界是 127

统计发现程序里大部分小整数都落在这个区间，缓存它们能显著减少对象创建；再往上缓存，收益下降而内存占用上升。这个值可以通过 -XX:AutoBoxCacheMax 调整，但业务代码不应依赖它。

7.3类型转换与最隐蔽的空指针

自动拆箱会在你「什么都没做」的时候抛异常。

字符串与数值互转是日常操作。Integer.parseInt("123") 返回 int，Integer.valueOf("123") 返回 Integer；后者会走缓存，前者不会。两者在格式错误时都抛 NumberFormatException，传入 null 则抛 NullPointerException。

更隐蔽的问题是自动拆箱。只要发生「包装类参与算术运算」「包装类赋值给基本类型」「包装类与基本类型比较」这三种情况，编译器就会插入 intValue()。如果此时对象是 null，直接 NPE——代码里完全看不到任何方法调用。

三处容易忽略的拆箱java
Integer count = null;
int total = count;                  // NPE：拆箱
// int sum = 1 + count;             // NPE：参与运算
if (count > 0) { }                  // NPE：与基本类型比较
金额计算必须用 BigDecimal

0.1 + 0.2 = 0.30000000000000004 不是 bug，而是二进制浮点的固有限制。BigDecimal 用十进制表示，能精确计算；构造时必须传字符串 new BigDecimal("0.1")，传 double 会把误差带进去。

7.4Character：字符的判定工具

char 是 16 位无符号整数，Character 提供了一整套分类判断。

因为 char 本质上就是 Unicode 码值，所以它可以直接和 int 互相转换：(int) 'A' 得 65，(char) 65 得 'A'。这个特性让「字符数字转数字」可以写成 '7' - '0'，比查表高效得多。

Character 的静态方法解决了「怎么判断一个字符是什么」这类问题：isDigit 判断数字、isLetter 判断字母（包括中文）、isWhitespace 判断空白、isUpperCase 判断大写。做输入校验、词法分析、统计字符时非常方便。

统计字符类型java
int letters = 0, digits = 0;
for (char ch : "Java 17".toCharArray()) {
    if (Character.isLetter(ch)) letters++;
    else if (Character.isDigit(ch)) digits++;
}
// letters = 4, digits = 2

7.5Object：所有类的共同祖先

你写的每个类，都默认继承了 Object 的六个方法。

其中最重要的是三个：toString 决定对象打印出来是什么样，equals 决定「两个对象是否相等」，hashCode 决定它在哈希表中的位置。默认实现都基于地址，所以自定义类几乎都需要重写。

方法作用默认行为
toString()返回对象的字符串表示类名@哈希码十六进制
equals(Object)判断是否相等比较地址（等价于 ==）
hashCode()返回哈希码由内存地址推导
getClass()获取运行时类返回 Class 对象，可用于反射
clone()浅拷贝需实现 Cloneable，否则抛异常

为什么每个实体类都该重写 toString？因为日志、调试、字符串拼接都会隐式调用它。不重写的话，你看到的是 Student@1b6d3586，排查问题时毫无信息量；重写后能直接看到字段值，这是最低成本的调试优化。

Object 作为参数类型时还有一个妙用：它能接收任何对象（包括自动装箱后的基本类型）。泛型出现之前，集合就是这么存数据的，这也是为什么集合里取出来的东西需要强转。

7.6equals 与 hashCode：必须成对重写

只重写一个，放进 HashSet 就会「存进去却找不到」。

契约只有一条，但必须记牢：equals 相等的两个对象，hashCode 必须相等；hashCode 相等的两个对象，equals 不一定相等（这叫哈希冲突，是允许的）。

为什么必须这样？因为哈希表（HashSet、HashMap）的查找分两步：先用 hashCode 算出桶的位置，再在桶内用 equals 逐个比较。如果两个「相等」的对象 hashCode 不同，它们会被放进不同的桶，第二步根本不会发生——于是 size 变成 2、contains 返回 false，逻辑彻底错乱。

equals 的四步写法java
@Override
public boolean equals(Object o) {
    if (this == o) return true;                       // 1 地址相同
    if (o == null || getClass() != o.getClass()) return false;  // 2 类型
    User u = (User) o;                                // 3 转型
    return id == u.id && Objects.equals(name, u.name); // 4 比字段
}

@Override
public int hashCode() { return Objects.hash(id, name); }

四步的顺序不能乱：先比地址（最快的短路）、再比类型（避免强转失败）、再转型、最后逐字段比较。字段比较用 Objects.equals 而不是 ==，因为它能安全处理 null。hashCode 则用 Objects.hash(...)，保证与 equals 使用同一组字段。

实际项目怎么做

IDEA 里 Alt + Insert 可以一键生成，Lombok 的 @Data 或 @EqualsAndHashCode 也能自动生成。但要知道它们生成的是什么，否则遇到「为什么两个对象 equals 为 true 却查不到」时无从下手。

小结这一章真正要记住的

Key takeaways

  1. 包装类解决三件事：泛型/集合、表达 null、提供工具方法。
  2. 装箱调 valueOf，拆箱调 xxxValue。 -128~127 走缓存，所以 == 在 127 上为 true、在 128 上为 false。
  3. 包装类比较永远用 equals。 不要依赖缓存区间，也不要混用 new。
  4. 自动拆箱是 NPE 的隐形来源。 赋值、运算、比较三处都会触发。
  5. 金额用 BigDecimal，构造传字符串。 double 的误差是二进制特性，不可避免。
  6. equals 与 hashCode 必须成对重写，使用同一组字段。 否则哈希表会失效。
  7. 实体类重写 toString，是最便宜的调试优化。

自测检查一下你真的懂了吗

为什么 List<int> 编译不过，List<Integer> 可以？
Java 泛型只接受引用类型，且在编译后会类型擦除、统一按 Object 处理，而基本类型不是 Object 的子类。所以必须用包装类，由自动装箱完成转换。
Integer a = 127, b = 127; a == b 和 Integer c = 128, d = 128; c == d 结果分别是什么？为什么？
true 和 false。-128~127 在 IntegerCache 范围内，valueOf 返回同一个缓存对象；128 超出范围，每次 new 新对象。
下面代码会抛异常吗？Integer i = null; int n = i;
会抛 NullPointerException。自动拆箱会调用 i.intValue()，而 i 不指向任何对象。
equals 与 hashCode 的契约是什么？只重写 equals 会有什么后果？
equals 相等则 hashCode 必须相等。只重写 equals 会导致「相等」的对象哈希值不同，在 HashSet/HashMap 中被放进不同桶，出现重复存储、contains 返回 false。
为什么金额计算要用 BigDecimal？构造时为什么建议传字符串？
double 用二进制浮点表示，无法精确表示 0.1 这类十进制小数，累加会产生误差；BigDecimal 用十进制表示，能精确计算。传 double 构造会把已有误差带进去，所以传字符串。
