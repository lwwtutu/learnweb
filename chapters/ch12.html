项目实战： 把知识变成一个能玩的东西

学完语法不等于会做东西。这一章用两个项目收口：石头迷阵练「数据建模 + 界面绘制 + 事件驱动」，人事管理系统练「分层设计 + 集合操作 + CRUD」。重点不在代码量，而在每一步为什么这么做。

约 120 分钟 7 个知识点 2 个完整项目 前置：全部前置章节

完成这两个项目，你将掌握

  • 把界面问题转换成数据问题
  • 用二维数组描述棋盘状态
  • 用坐标系统管理组件位置
  • 写出清晰的移动与胜利判定
  • 理解「可解性」这类隐式约束
  • 用分层思想组织一个 CRUD 系统
  • 知道下一步该学什么

12.1先想清楚要做什么

石头迷阵是 4×4 的数字华容道：16 格中有一格为空，滑动方块把图拼回去。

拿到一个需求，第一步不是打开 IDE，而是把它拆成可验证的小目标。这个项目可以拆成六件事：窗口能显示、图片能排成网格、方向键能让方块动、拼好能判断胜利、能重新开始、能计时。每一项都能独立跑通，再组合起来。

核心抽象

整个项目只围绕一个数据结构：4×4 的二维数组。数组里存 1~15 的数字和 0（代表空），数字对应图片编号。界面只是这个数组的「投影」——数组一变，重新渲染即可。把界面问题转换成数据问题，是所有游戏开发的通用思路。

项目结构text
stone-maze/
└── src/
    ├── com/itheima/MainFrame.java   // 界面 + 核心逻辑
    └── image/1.png ~ 15.png         // 拼图块，100×100

为什么不一开始就拆成「模型层 + 视图层」？因为这是教学项目，规模小，强行分层只会增加理解成本。但如果要继续扩展（加排行榜、多人对战），就应该把数据与界面分开——这正是第 12.6 节人事管理系统要演示的。

12.2用数组描述世界

数组的下标天然对应屏幕坐标，这是最省事的一步。

定义 int[4][4] data，data[i][j] 表示第 i 行第 j 列放的是哪张图。0 表示空位，显示时不设图标，背景自然露出。再定义一个同样内容的 target 数组存目标状态，用于胜利判定——这样判定就退化成「逐格比较两个数组」。

把「数字」和「图片」解耦带来一个好处：调试时可以直接打印数组看状态，不用盯着界面猜；单元测试也能脱离界面进行。这是数据建模的第一条经验——能用数据表达的，就不要用界面状态表达。

12.3把数组画到屏幕上

绝对布局 + 16 个 JLabel，最直白也最可控。

Swing 的布局管理器会自动排布组件，但对棋盘这种「每格位置固定」的场景反而是束缚。所以这里用 setLayout(null) 关闭自动布局，手动给每个 JLabel 设坐标：第 i 行第 j 列的位置就是 (j × 100, i × 100 + 40)，40 是给顶部信息栏留的空间。

创建 16 个格子java
for (int i = 0; i < 4; i++) {
    for (int j = 0; j < 4; j++) {
        JLabel label = new JLabel();
        label.setBounds(j * 100, i * 100 + 40, 100, 100);
        cells[i][j] = label;
        add(label);
    }
}

然后写一个 refresh() 方法，遍历数组给每个格子设置图标（0 则清空）。所有会改变状态的操作——移动、打乱、重启——最后都调用它。「状态变化 → 统一重绘」这个模式，是后面所有前端框架（React、Vue）的核心思想。

图片加载不出来的排查顺序

① 确认 image 目录在 src 下、编译后出现在 out 目录；② 确认文件名与代码拼接的字符串完全一致（区分大小写）；③ 用 new ImageIcon(path).getIconWidth() == -1 判断是否加载成功。路径问题是这类项目最常见的卡点。

12.4移动：三次交换与一道边界

所谓「移动方块」，本质是「空白格与相邻格交换」。

用户按方向键时，真正发生的不是「方块滑过去」，而是数组里两个元素互换。所以 move(dr, dc) 只需要三步：找到 0 的位置、算出目标坐标、交换两个位置的值。其中 目标坐标必须做边界检查，否则空白格在最右列时按右键就会数组越界。

交换与判定java
int[] zero = findZero();          // 找到 0 的坐标
int r = zero[0] + dr, c = zero[1] + dc;
if (r < 0 || r > 3 || c < 0 || c > 3) return;   // 越界忽略

data[zero[0]][zero[1]] = data[r][c];
data[r][c] = 0;
steps++;
refresh();

胜利判定同样简单：逐格与 target 比较，全部相同就赢。这里有个设计选择——是在移动后判定，还是在每次重绘时判定？前者更明确（只有移动才可能赢），后者更省事但会在打乱阶段误触发，所以选前者。

键盘事件要用 KeyListener 监听方向键。注意 Swing 的按键事件依赖焦点，点击菜单或切换窗口后焦点会丢失，导致「按了没反应」。解决办法是在重启后调用 requestFocusInWindow()，或改用 KeyBindings 绑定到根面板。

12.5打乱：一个容易被忽略的数学约束

随机排列只有一半是可还原的，直接 shuffle 会做出一半无解的题。

这是本项目最有价值的一个知识点。数字华容道的可解性由逆序数的奇偶性决定：只有逆序数为偶数的排列才能通过合法移动还原。随机全排列时，奇偶各占一半，所以有一半概率玩家永远拼不出来。

解决办法很聪明：从完成态出发，做 200 次合法的随机移动。因为每一步都是合法逆操作，得到的任何状态必然可还原。这个技巧叫「反向打乱」，在洗牌、生成谜题、随机游走中都通用。

反向打乱java
for (int k = 0; k < 200; k++) {
    while (true) {
        int[] d = dirs[random.nextInt(4)];
        int[] zero = findZero();
        int r = zero[0] + d[0], c = zero[1] + d[1];
        if (r >= 0 && r < 4 && c >= 0 && c < 4) {
            data[zero[0]][zero[1]] = data[r][c];
            data[r][c] = 0;
            break;                  // 越界就换方向重试
        }
    }
}

计时的实现很轻量：用一个每秒触发一次的 javax.swing.Timer，回调里让秒数加一、更新标签。注意 Timer 的回调运行在事件分发线程，所以可以直接改界面；如果做耗时计算则必须放到后台线程。

12.6第二个项目：分层的人事管理系统

同样一个系统，写法可以很随意，也可以很「工程」。

最直接的写法是把所有逻辑塞进 main 方法：用 Scanner 读输入、用 switch 分派、用 ArrayList 存数据。能跑，但一个月后你就不敢改了。更合理的做法是按职责分三层：实体（Employee）只描述数据，服务（EmployeeService）负责业务逻辑，界面（HrApp）只管输入输出。

分层的收益在改动时最明显。想把控制台换成 Swing 界面，Service 一行都不用改；想加「按薪资排序」，只在 Service 里加方法；想写单元测试，直接测 Service，不涉及输入输出。

Service 的核心职责java
public class EmployeeService {
    private final List<Employee> list = new ArrayList<>();

    public boolean add(Employee e) {
        if (findById(e.getId()) != null) return false;   // 业务规则：工号唯一
        return list.add(e);
    }

    public Employee findById(String id) {
        for (Employee e : list) if (e.getId().equals(id)) return e;
        return null;
    }
}

注意 findById 返回 null 表示「没找到」，这是 Java 里常见的约定（集合的 get 也类似）。调用方必须判空，否则下一步就 NPE。更现代的做法是返回 Optional<Employee>，用类型强制调用方处理「可能不存在」的情况。

菜单循环用 while (true) + switch，退出时 return。Scanner 读数字时统一用 nextLine() 再解析，可以避开「nextInt 后 nextLine 读到空串」的经典坑。

这个项目已经具备框架的雏形

Employee 是 Model，Service 是业务层，HrApp 是 View。后面学 Spring Boot 时你会发现，所谓「三层架构」就是这套东西的工程化版本，只是对象创建交给容器、输入输出换成 HTTP。

12.7接下来往哪走

JavaSE 到这里完整了，但真正的工程能力在下一段。

方向要学什么学完能做什么
集合与并发HashMap 原理、线程池、锁处理高并发数据
IO 与网络文件流、NIO、Socket、HTTP读写文件、调用接口
数据库SQL、JDBC、连接池数据持久化
Web 后端Maven、Spring Boot、MyBatis写 REST 接口
工程能力Git、单元测试、日志、调试参与真实项目

建议的顺序是：先把集合框架补齐（HashMap 是面试与实战的双重重点），再学 IO 与 JDBC 让数据能落地，最后进 Spring Boot。不要在语法细节上无限打转——真正的进步来自「做一个完整的东西」，而不是「再看一遍教程」。

最后，给这两个项目各加一个功能，作为检验：石头迷阵加「排行榜」（需要排序、文件持久化），人事系统加「按薪资排序 + 姓名模糊查询」（需要比较器、字符串匹配）。能独立完成，说明这一门课真的学完了。

小结这一章真正要记住的

Key takeaways

  1. 先拆需求，再写代码。 每个小目标都能独立跑通，组合起来才可控。
  2. 把界面问题转换成数据问题。 数组是唯一真相，界面只是投影。
  3. 状态变化 → 统一重绘。 这是所有 UI 框架的核心模式。
  4. 移动的本质是交换，边界检查必须先做。
  5. 随机打乱要保证可解性。 反向移动是通用解法。
  6. 分层不是形式主义，是为了改得动。 换界面、加功能、写测试都靠它。
  7. 学完的标志是能独立做出东西，不是看完教程。

自测项目复盘

为什么石头迷阵用二维数组，而不是 16 个独立变量？
数组能用双重循环统一处理绘制、刷新、判定，下标与屏幕坐标一一对应；16 个变量要写 16 段重复代码，无法用循环抽象，也无法做整体比对。
移动逻辑为什么必须先判断边界再交换？
先交换会导致下标越界（如空白在最后一行还向下移动）。正确顺序是：算出目标坐标 → 判断在 0~3 范围内 → 再交换。
为什么用「反向随机移动」打乱，而不是直接 shuffle 数组？
数字华容道只有逆序数为偶数的排列可还原，随机全排列有一半无解。从完成态做合法移动，得到的任何状态必然可还原。
人事系统中 Service 层为什么要单独抽出来？
把数据操作与界面交互解耦：换交互方式（Swing / Web）时 Service 不用改，也便于单元测试。这是单一职责原则的直接体现。
如果给石头迷阵加排行榜，你会怎么设计？
新建 Score 类（玩家、步数、用时），用 List 保存，Comparator 先比用时再比步数排序，持久化可用对象序列化或 JSON 写文件。正好用上集合、比较器与 IO。
